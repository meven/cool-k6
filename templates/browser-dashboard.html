One chart per document and user pool, tracked across commits. The thick line is the instructions that the document kit executed, and the dashed grey line those of coolwsd. Left axis: load, feedback and edit times (ms), or the instructions (G) when the times are hidden. The buttons in the legend show or hide each group. Right axis: memory (MB), the document's own footprint, the browser heap, the page process, and the coolwsd process peak. Click a point for detail.

Each point is one run (one COOL commit) of the document named under the chart title, which is the file that test opens through the WOPI host. Times are ms averaged over the run (left axis). Memory (right axis, dashed) is the peak during the run: COOL document memory is the document's own footprint: the kit's Private_Dirty from COOL's getMetrics endpoint on a plain run, or the document kit's proportional set size sampled from /proc when the point comes from a flamegraph capture, which runs its own COOL, and browser heap is the page's JS heap. The page process is the resident size of the Chromium renderer that runs the page, sampled from /proc during the test: on top of the JS heap it holds the DOM, the decoded images and the canvas pixels of the tiles. The coolwsd peak is the largest resident size of coolwsd and its forkit together during the test, sampled from /proc. The forkit holds the preloaded engine, most of the figure. Runs from before that sampling show the resident high-water mark (VmHWM) of the capture's own coolwsd instead. The stacked bar behind each point breaks the document kit's resident memory into the engine libraries it maps, other mapped files, what the fork handed it (mostly the dictionaries the parent preloaded), and what the document itself wrote. Only the last layer is the document's own cost; the first three are shared with every other document on the machine, which is why the resident total is several times what one more document actually adds. The instruction lines have a scale of their own, which the left axis shows when the times are hidden. They count only the window perf was attached for, which opens after the server is up, so they describe the test and not a whole process life. A busy machine slows the times but does not change the instruction counts, so a busy run stays on the instruction lines. A rising line across commits is a regression. A faded point was measured on a busy machine: a fixed probe ran slower than usual during the run, or the hypervisor took CPU time from the VM, so its times are not comparable. The run detail of each point gives the commits since the previous point, as a git log range and, for a GitHub source, a link that lists them. When a run was also captured under perf, its point shows the plain times and the run detail lists the times under perf beside them. The times under perf are within the noise of a plain run, so a run measured under perf alone stays on the same lines. Each run's detail embeds that run's own document flamegraph (k6-flamegraph profiling the kitbroker_* document kit while the document is open, captured with its own single-kit COOL) and can put a second run beside it to compare two commits. A capture is only ever shown for the run it was taken in, and the badge on each chart says how many of that document's runs were profiled.

Schedule

The runs of the VM from 12 hours ago to 12 hours ahead, in the time zone of this browser: the runs of main, which the timer starts every hour when main has a new commit, the queued Gerrit changes, and the units started by hand with systemd-run. A queued change is built and measured once the run before it has ended, so its time is the earliest it can start. A change is accepted when its patch set was uploaded from an allowed domain, and the patch set is kept as it was queued. Pause on the main row stops the timer from starting runs of main until Resume; a run of main that has started goes on to its end.

Leave the start empty to run as soon as possible.

History

The runs on the charts, newest first, with the time each started, in the time zone of this browser. The commits are those the run measured for the first time: since the previous run of its branch, or since its base on main for a change. The data link opens the run's folder, with its logs, metrics and flamegraphs. A deleted run leaves the store and the charts.

Capacity

The capacity runs of the VM, newest first, which deploy/run-capacity starts. Users join in a staircase and type in the documents of the run's scenario, and coolwsd, forkit and the kits run on a limited number of cores and memory. A stage passes when the 95th percentile of the edits and of the loads stays under its target, under 1% of the sessions fail, and the kernel kills no process of the server for lack of memory. The capacity is the largest stage that passed, up to the first that did not, so a run where every stage passed only gives a lower bound. Runs from before 9 November 2026 did not record when the OOM kills happened, so one with any OOM kill has no capacity.

A queued run builds the change or the ref first and waits for the other runs, as the Schedule tab lists them. A heap profile has one stage of 10 users for 3 minutes.
